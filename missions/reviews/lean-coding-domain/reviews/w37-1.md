## (1) seedIndex: the race is closed
Without USE_NSEC (the default build), git rechecks an entry's content when the entry's mtime second is not older than the index's mtime second. A same-size in-place edit keeps the size and the inode, and its ctime second matches the one recorded at the add. So the recheck is the only thing that catches the edit, whatever `trustctime` is set to. A fresh copy mtime turns the recheck off; keeping the source mtime turns it back on. Going through `Date` drops sub-millisecond precision, which makes the timestamp earlier and only flags more entries, so it errs safe. `trustctime=false` only stops a false pass in the test when the setup crosses a second boundary.

- **L-1** `git.ts:183-184` stats the index after copying it. If git rewrites the real index between the two calls, the race is back. Stat before copying to fail safe. The window is tiny (same order as `827948c8`).

## (2) Re-entry bound
The loop is bounded: there are two stages, and each re-entry needs a kind that has not re-entered yet. It cannot loop. Worst case is 4 builders, 4 passes and 2 reviewers. The token budget is checked before every stage (`run-build.ts:1227`) and the deadline aborts on time, so running over ends `failed`. A run with no re-entry behaves as before.

- **M-1** `run-build.ts:647`: the trigger is broader than the W3-OD-5 fix ("only when the re-entering signal never ran in the previous pass"). Any kind no builder has been sent yet qualifies. Probe: mutation fails in pass 1 while verify passes, so builder-2 runs. Builder-2 breaks verify in pass 2, and builder-3 still runs; the run ends `done` with 3 builder calls. Under the narrow rule it ends `blocked`. Brief §4.7B.6 and WP4c still say "once". Fix: allow the second re-entry only when every new kind was missing or `data.skipped` in the previous pass, or have the human rule "one per kind" and amend the brief. Add a test that pins the boundary.
- **L-2** `run-build.ts:647-650`: "one per kind" relies on verify running before mutation. If the order is reversed, verify can go back to the builder a second time.
- **L-3** `run-build.ts:1031-1034` says "after two re-entries: verify" when verify re-entered only once.
